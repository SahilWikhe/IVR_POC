# Canonical confirmation and staff call control

The call-control modules generate provider instructions for an immutable request readback and an approved staff transfer, and update an existing Twilio call through the official SDK. Their deterministic tests use synthetic call IDs and fake HTTP adapters. **Actual Twilio acceptance, speech recognition, timing, transfer callbacks, and carrier behavior remain unverified.** These modules do not purchase numbers, change incoming-number routing, create bookings, or make standalone outbound calls.

`packages/connectors/src/telephony.ts` owns the server-authored TwiML builders. `apps/voice-gateway/src/control.ts` owns the bounded REST dispatcher. The API remains responsible for authorization, immutable proposal binding, durable operation state, signed callback validation, and atomic confirmation. A model or caller must never supply TwiML, callback URLs, a transfer destination, or an operation identity.

## Request readback protocol

`buildReadbackTwiml({ publicUrl, confirmationToken, readback })` emits the canonical readback as a top-level `<Say>` **before** the speech `<Gather>`. Twilio processes that readback before opening this confirmation gather. Keeping the canonical text outside the gather prevents speech recognition from affirming an interrupted or partially played canonical readback. This establishes a provider instruction order; it does not prove that a caller paid attention or understood the words.

The gather accepts speech or one keypad digit, posts to `/twilio/confirmation/<token>`, uses a five-second input timeout, automatic end-of-speech detection, a five-second maximum utterance, and yes/no recognition hints. Its explicit prompt offers yes or **1** to save an **unconfirmed request for staff review**, and no or **2** to cancel. This does not book a table. `actionOnEmptyResult=true` requests the same callback when the caller gives no input. Mixed nonempty speech and digits are rejected; only digit 1 can affirm through the keypad. Speech uses the existing exact affirmative allowlist. Optional confidence must be a finite value from 0 to 1, but is diagnostic metadata and does not decide whether an otherwise valid explicit affirmative saves. Twilio does not guarantee the score's accuracy or presence; an arbitrary cutoff rejected repeated recognized "Yes" answers in the local test.

No input or an unsupported single digit can receive one additional confirmation prompt when the same proposal remains valid and both the original call and confirmation deadlines have at least 20 seconds left. The API retains the original details, stores one new random retry-token hash, and returns `buildConfirmationRetryTwiml` directly in the callback response. It does not issue another REST call update or restart the model. This fixed, short Gather follows the already-completed canonical readback; it does not replace or modify the proposal. The verified first callback moves the control to `ACCEPTED`, so a late uncertain/rejected dispatch acknowledgment cannot erase the pending request. The original deadline is never extended.

Both tokens are bound to the same call and proposal and have separate existing-format replay receipts. Identical first callbacks return the same active retry; altered payloads conflict. Once the retry is complete, revoked, or expired, replaying the first callback returns inert ending instructions. Retry callbacks recheck current policy, proposal/configuration integrity and expiry. A second uncertain answer, decline, correction, insufficient time, or failed authority check cannot save. Successful simultaneous retries commit exactly one inbox item. The new optional retry hash is stored in the existing strict JSON call record; legacy records have no retry authority and need no SQL migration.

The callback must verify the official Twilio signature over the configured HTTPS URL and all form fields, expected provider account, original parent call, server-issued token, tenant, call generation, proposal/configuration revision, expiry, and persisted canonical details. Only an explicitly permitted affirmative result can admit the atomic request save. Blank, ambiguous, negative, stale, conflicting, duplicate, or mismatched input must never create another request. Recognition confidence does not verify identity or establish consent; the verified current callback and exact affirmative remain necessary. A caller hanging up before confirmation must not commit.

An API-issued confirmation token binds the complete immutable proposal. Neither the gateway nor a model may substitute its own text. The canonical readback allows up to 2,000 characters so a supported 1,500-character message plus name, callback number, and consent framing fits. Render and validate the TwiML **before** admitting or persisting a control command: escaped XML must remain within the 4,000-character dispatch limit. A serialized oversized message must produce a recoverable proposal error, not a prepared command that can never dispatch.

The document includes a defensive message that saving could not be confirmed and `<Hangup>` after the gather. The action response controls the normal next step; the trailing message is not a substitute for a configured failure URL. If the application callback is unreachable, provider-hosted fallback TwiML must clearly say that saving could not be confirmed and ask the caller to try again later, or use an approved independent staff destination. The restaurant's public number may forward into the same failed route. Fallback must never claim that the request was saved. The operator must configure and test this independent fallback in Twilio; no external fallback resource is provisioned here. See [offline fallback preparation](PHONE_FALLBACK.md). If saving has an uncertain database/network result, fallback must preserve that uncertainty rather than assert absence or success.

## Staff transfer protocol

`buildTransferTwiml({ publicUrl, transferToken, destination, staffLabel, remainingSeconds })` emits a fixed short trying-staff message and `<Dial answerOnBridge="true">`. Its action posts to `/twilio/transfer-result/<token>`. The `<Number>` noun posts initiated, ringing, answered, and completed callbacks to `/twilio/transfer-status/<token>`.

The API supplies `remainingSeconds` from the original admitted call's persisted deadline, not from caller/model input or a newly restarted timer. Only integer budgets from 25 to 600 seconds are accepted. The builder reserves 15 seconds: eight for the fixed announcement, five for provider ringing-time variance, and two for control/fallback overhead. Requested ringing is the smaller of 20 seconds or the remaining budget after that reserve and a minimum five-second bridge; the bridge time limit receives the rest. For 25 seconds remaining, ringing and bridging each receive five seconds. For 300 seconds remaining, ringing receives 20 seconds and bridging 265 seconds. The supplied staff label remains validated but does not extend the spoken announcement.

Recheck elapsed time at dispatch and reject commands whose remaining allowance has expired; persisting a document at preparation must not freeze a fresh full call budget for a later send. TwiML timing is not a wall-clock guarantee: speech rate, provider ringing variance, callback latency, and fallback may vary. Preserve the authoritative overall call deadline and provider/gateway termination controls independently. Actual deadline and transfer timing need dedicated-number acceptance tests.

The API selects the currently approved restaurant destination, validates enabled transfer policy, and rejects a destination equal to the dedicated Twilio number or the restaurant's forwarded public number. Hours-based staff routing is not enforced by this module and needs a separately implemented policy before claiming that availability is checked. The builder validates E.164 syntax and a bounded staff label; it cannot independently establish ownership, opening hours, or forwarding-loop freedom. All callback origins come from the configured HTTPS origin, and tokens are 256-bit random values encoded as 64 lowercase hexadecimal characters. The SDK escapes text as XML. Recording is not enabled.

Callback verification must distinguish parent-call completion from child-leg progress. Validate signatures and bind the provider account, original parent call, authorized destination, persisted transfer token/generation, and child call ID. Account/call bindings differ between an inbound parent and the outbound child; blindly requiring the inbound `To` value for every child callback is incorrect. Child-leg `answered` evidence means the line answered. A voicemail system or automated attendant can answer, so this event does not establish human pickup or staff acknowledgement. Never claim successful human handoff from the REST admission response alone.

Busy, no-answer, canceled, failed, contradictory, missing, and out-of-order callbacks require honest caller fallback and durable outcomes. The root workflow owns that handling and replay policy. Replacing the media stream with provider-hosted readback or dialing ends the previous stream; its cleanup must not prematurely end the parent call or revoke the pending control action.

## REST dispatch and uncertainty

`createCallController({ accountSid, authToken, publicUrl, maxCallSeconds? }, { transport?, timeoutMs? })` exposes `dispatch(callSid, twiml, signal?)` and returns one of:

| Result                      | Meaning and required caller behavior                                                                                                                                              |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `accepted`                  | Twilio acknowledged the update. Wait for authenticated confirmation/transfer evidence; this proves neither playback nor staff pickup.                                             |
| `rejected` plus a safe code | Local validation/cancellation prevented dispatch, or a recognized explicit provider rejection was received. Do not expose raw vendor bodies.                                      |
| `unknown`                   | Timeout, connection reset, server error, response parse failure, or cancellation after admission cannot establish whether Twilio accepted the update. Do not retry automatically. |

The SDK client is created separately for each dispatch. The request is constrained to `POST https://api.twilio.com/2010-04-01/Accounts/<configured-account>/Calls/<validated-call>.json`. Environment edge/region overrides cannot select another host. Redirects are disabled. The request defaults to a 4.5-second deadline and rejects a configured timeout greater than five seconds. SDK automatic retries are disabled, including rate-limit retries. The dispatcher forwards cancellation to the SDK HTTP adapter and also enforces its own deadline for injected transports that ignore cancellation. A late success cannot transform an already returned unknown result into an automatic retry opportunity.

When supplied, `maxCallSeconds` must be an integer from 15 to 600 and adds `timeLimit` to that same call-update request alongside `twiml`; it does not make an additional REST write. The gateway supplies the original configured total call cap. It must not reset this cap to a new total allowance on stream resume or replace it with a caller-selected value. The SDK describes this field as the maximum duration of the call. Its actual relationship to elapsed call time and an updated/resumed call remains a live acceptance requirement. Keep the original persisted deadline, remaining-budget checks, and cleanup independent; this request parameter does not establish a fully verified overall cap.

Only a successful durable dispatch claim may call this method. Persist the immutable command and bind it to the call/controller generation before admission; atomically claim one dispatch winner; record dispatch admission before the external send; and persist the result. If the process crashes after admission or result reporting fails, preserve an unknown outcome. Authenticated later callbacks may resolve uncertainty. There is no safe transparent retry of an admitted command merely because the gateway disconnected.

Configuration validation reports safe field errors. The client explicitly disables SDK debug logging and discards temporary SDK diagnostic request/response state after dispatch. No credentials, callback tokens, canonical caller details, or provider response bodies belong in application logs. Canonical payload storage and retention are separate from broad raw transcript retention.

## Verification and sources

Run `pnpm exec vitest run tests/call-control.test.ts`. The tests exercise canonical instruction ordering, no-input callback behavior, no-save fallthrough, XML escaping and serialized limits, E.164 and callback-origin boundaries, child-leg callback configuration, predispatch rejection, explicit vendor rejection, uncertain network outcomes, deadlines, late completion, concurrent cancellation isolation, and actual SDK request serialization through a fake HTTP adapter. They do not need vendor credentials or perform network writes.

Implementation was checked against installed **Twilio Node 5.13.1** source and declarations, including `VoiceResponse.d.ts` gather/dial/number attributes, `call.d.ts`/`call.js` update serialization, and `RequestClient.js` timeout, redirects, Axios cancellation, and retry behavior. Public sources for account acceptance review are:

- [Twilio Node TwiML implementation](https://github.com/twilio/twilio-node/blob/main/src/twiml/VoiceResponse.ts)
- [Twilio Node HTTP client](https://github.com/twilio/twilio-node/blob/main/src/base/RequestClient.ts)
- [Twilio Gather](https://www.twilio.com/docs/voice/twiml/gather), including `actionOnEmptyResult`, speech timeout, and nested prompts
- [Twilio Dial](https://www.twilio.com/docs/voice/twiml/dial) and [Number](https://www.twilio.com/docs/voice/twiml/number), including action and child-leg status callbacks
- [Twilio Call resource](https://www.twilio.com/docs/voice/api/call-resource), including updates to an existing call

Use a dedicated authorized test number and explicit sandbox flags for actual acceptance. Twilio test credentials do not provide a real Media Streams conversation; the Twilio WhatsApp Sandbox is a separate messaging feature. Real voice testing uses a voice-capable test number on an appropriate account and can incur provider charges. Keep restaurant customer forwarding disabled until confirmation, transfer, fallback, recovery, and release gates are verified.
