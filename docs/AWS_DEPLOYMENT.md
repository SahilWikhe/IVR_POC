# AWS deployment and operations

The repository contains reviewable CloudFormation templates, container entrypoints, and GitHub workflows for a private-data AWS staging installation. No AWS account has been connected, infrastructure provisioned, secrets uploaded, DNS changed, or deployment performed by this change. Automatic deployment remains off until explicit repository readiness variables and protected environments are configured. Production deployment is blocked by both the deployment helper and the application startup gate.

Use [implementation status](IMPLEMENTATION_STATUS.md), [identity operations](IDENTITY_OPERATIONS.md), [Auth0 setup](AUTH0_SETUP.md), and [privacy/recovery operations](PRIVACY_OPERATIONS.md) alongside this runbook. A green template lint or CI run does not verify deployed IAM, provider behavior, RDS TLS, or restoration.

## Stacks and traffic

| Stack                             | Responsibilities                                                                                                                                                                | Deletion behavior                                                                                                                                                                                   |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `namespace-environment-data`      | VPC, subnets, NAT, security groups, private DNS zone, private PostgreSQL 17 RDS, encryption key, recovery-authority DynamoDB table, ECR repository, audit bucket and CloudTrail | Human-controlled. Database and recovery table have deletion protection. Persistent resources have `Retain` and `UpdateReplacePolicy: Retain`. Enable stack termination protection during bootstrap. |
| `namespace-environment-bootstrap` | Environment-bound GitHub OIDC role, scoped application CloudFormation execution role, task-role permissions boundary                                                            | Human-controlled; roles/boundary are retained. CI cannot update this stack.                                                                                                                         |
| `namespace-environment-app`       | ECS cluster/tasks/services, two HTTPS ALBs, target groups, hostname records, WAF, log groups, and alarms                                                                        | Explicit application cleanup can delete services/ALBs. Log groups are retained. No database, authority table, network, key, private zone, or repository allocation belongs here.                    |

The public ALB routes separate sibling hostnames, such as `app.example.com` and `voice.example.com`, to API/dashboard and voice gateway respectively. It uses an existing region-matched ACM certificate covering both names. There is no plaintext listener. The private ALB accepts HTTPS only from the voice task security group and forwards to the API. A retained private zone for the app hostname points that hostname at the private ALB inside the VPC; `API_INTERNAL_URL` therefore remains HTTPS with ordinary certificate validation. Use sibling hostnames: nesting the voice hostname beneath the private app zone would shadow public resolution.

The public listener denies `/internal` and `/internal/*`. The public WAF additionally decodes, normalizes, and lowercases URI paths before blocking the `/internal` prefix. Internal API endpoints also require the configured service credential and recovery authority. Real-ALB acceptance must exercise `/%69nternal/voice/context`, `/internal%2Fvoice/context`, path normalization, and the ordinary paths; the static configuration does not establish AWS normalization behavior. The private ALB has no public WAF association.

Fargate tasks run without public IPs, under separate execution/runtime roles, as user `10001` with a read-only root filesystem and ECS Exec disabled. Security groups admit API/voice traffic only from their ALBs and database traffic only from API, worker, and migration groups. The voice task cannot connect directly to PostgreSQL. API trusts forwarded client identity only from the configured public/private ALB subnet CIDRs; that trust relies on the accompanying security-group path.

Staging defaults to one NAT gateway and a single-AZ database. `HighAvailability=true` adds a second NAT and Multi-AZ database; production data configuration requires it. One API, voice, and worker task is the current supported service configuration. This is an initial staging topology, not evidence of production availability or safe arbitrary horizontal scaling. Rolling deployments temporarily overlap tasks. Active phone draining, long-call interruption, rollout overlap, WAF callback compatibility, and provider failure behavior require live acceptance before enabling calling.

## Manual account bootstrap

Perform this only after account access, region, expected cost, domain, and provisioning authorization are supplied. No checked-in workflow provisions data or bootstrap stacks.

1. Choose namespace/environment and two availability zones. Confirm the selected PostgreSQL **17 minor** and instance class are offered in the region; `PostgresEngineVersion` is explicit rather than an invented default. Review NAT, two ALBs, RDS, backups, WAF, CloudWatch, DynamoDB, and audit storage charges. Retained resources continue accruing charges after application cleanup.
2. Review and create the data stack with its app hostname, engine minor, and HA choice. Enable stack termination protection; verify database/table deletion protection, backup/PITR settings, and encryption. Establish backup ownership and a tested restore process.
3. Verify the account-wide GitHub OIDC provider for `https://token.actions.githubusercontent.com`, audience `sts.amazonaws.com`; pass its existing ARN to bootstrap. An account administrator must create/verify the AWS ELB and ECS service-linked roles first (`AWSServiceRoleForElasticLoadBalancing`, `AWSServiceRoleForECS`); CI deliberately has no `iam:CreateServiceLinkedRole`. Verify any other service prerequisites through a nonexecuted change set.
4. Using the RDS-managed master secret through a controlled operator session, initialize the required schema and separate native login identities. Give the API login only `hostline_app` and `hostline_auth` membership (the latter executes approved auth functions, without broker membership). Give the worker login `hostline_app` and `hostline_worker` membership for current checkpoint and job transactions. Keep migration on its distinct migration identity. Runtime logins must not inherit migration, privacy, owner, superuser, or broker administration privileges. The API does not run the standalone worker's jobs (`RUN_INTERNAL_JOBS=false`). See the native-role checks and [identity operations](IDENTITY_OPERATIONS.md).
5. Create four distinct Secrets Manager JSON secrets encrypted with the data key, then pass only their ARNs to bootstrap/application configuration. Configure Auth0 application callbacks, MFA, exact issuer/client, and reviewed database memberships. No public demo sign-in is deployed.
6. Review/create the bootstrap stack, then configure protected GitHub environments and the variables below. Check effective IAM using account-specific validation and a change set before enabling automation. The CI role cannot read secret values or update the retained-data stack. Its CloudFormation role has read-only EC2 metadata, hostname-scoped DNS writes, namespaced ALB/ECS/log/role management, and mandatory task-role boundaries. Some allocation and metadata APIs necessarily use `Resource: "*"`; these are documented in the template and do not establish a general-purpose deployment identity.
7. Initialize the independent recovery manifest and matching restricted database checkpoint through the separately authorized operator procedure. Bind the **actual** RDS `DbiResourceId`, instance identifier, endpoint/port, installation UUID, and epoch. Keep services quarantined until current security reconstruction and contiguous journal coverage are independently approved. Infrastructure creation and migration do not set `securityReauthorized` or approve a checkpoint. Fresh missing authority/checkpoint yields `/api/ready` 503 and a paused worker.
8. Inspect templates and IAM, run the pre-deployment checks, activate staging with calling flags still false, and verify the acceptance checklist. Actual live calling and production release remain separate reviewed milestones.

## Secrets and runtime configuration

Secrets never belong in CloudFormation parameters/outputs, GitHub variables, command-line arguments, commits, or workflow logs. ECS reads only the corresponding service's JSON keys from its referenced secret. URI credentials must be correctly percent-encoded in the secret itself. Do not upload secrets in chat.

| Secret    | Required JSON keys                                                                                                                                                                           |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API       | `DATABASE_URL`, `SESSION_SECRET`, **distinct** `SESSION_ENCRYPTION_SECRET`, `OIDC_CLIENT_SECRET`, `VOICE_SERVICE_TOKEN`; `TWILIO_AUTH_TOKEN` only when the optional status reader is enabled |
| Voice     | `TWILIO_AUTH_TOKEN`, `OPENAI_API_KEY`, `VOICE_SERVICE_TOKEN` when live voice is enabled                                                                                                      |
| Worker    | `DATABASE_URL` for the separate restricted worker login                                                                                                                                      |
| Migration | `DATABASE_MIGRATION_URL` for the dedicated migration login                                                                                                                                   |

All native task connections use `DATABASE_CA_FILE=/opt/hostline/certs/rds-global-bundle.pem`. The image fetches the public official RDS CA bundle over verified HTTPS at build time and parses the certificates. Database TLS verifies the server certificate/hostname with that CA; ambiguous or weaker DSN SSL options are rejected. Do not disable TLS verification to repair a deployment. Actual image build and region-specific RDS TLS still require verification.

The one image exposes these fixed commands: `node apps/api/dist/index.js`, `node apps/voice-gateway/dist/index.js`, `node apps/worker/dist/index.js`, and one-off `node apps/migrate/dist/index.js`. API listens on 3001 and serves the compiled dashboard; voice listens on 3002. Hosted tasks bind `0.0.0.0`. Runtime OIDC/native services require independent recovery authority. The RDS identity is read from AWS and checked against the expected binding, manifest, and connection target; environment variables alone do not prove the database's identity.

## GitHub environment settings

Create `staging` and `production` environments with **main-only deployment branch rules**. Require reviewers for production and privileged operations as appropriate, and prevent approval bypass. The role's OIDC subject is exactly `repo:SahilWikhe/IVR_POC:environment:staging` or `:production`, with audience `sts.amazonaws.com`. Environment-based subjects do not themselves contain a branch claim: workflow branch guards plus protected environment branch rules enforce main-only use. Keep these settings under reviewed administration.

Repository-level `AWS_STAGING_READY`, `AWS_PRODUCTION_READY`, and `AWS_OPERATIONS_READY` default absent/off. Set an exact `true` only after configuring the intended environment and verifying its readiness. `AWS_PRODUCTION_READY=true` still cannot bypass the code gate. Credentials are obtained only by the eligible job through short-lived OIDC; do not add long-lived AWS keys to GitHub.

Set these non-secret **environment variables** in GitHub:

| Variable group       | Names                                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Fixed account/roles  | `AWS_ACCOUNT_ID`, `AWS_REGION`, `AWS_NAMESPACE`, `AWS_DEPLOYMENT_ROLE_ARN`, `AWS_CLOUDFORMATION_ROLE_ARN`, `AWS_RUNTIME_BOUNDARY_ARN`       |
| HTTPS/DNS            | `AWS_APP_DOMAIN`, `AWS_VOICE_DOMAIN`, `AWS_CERTIFICATE_ARN`, optional `AWS_PUBLIC_HOSTED_ZONE_ID`                                           |
| Auth0                | `AWS_OIDC_ISSUER`, `AWS_OIDC_CLIENT_ID`                                                                                                     |

| Scope/recovery       | `AWS_VOICE_TENANT_ID`, `AWS_RECOVERY_INSTALLATION_ID`, `AWS_RECOVERY_EPOCH`                                                                 |

Namespace must match all three stacks and contain 3–13 lowercase letters/digits/hyphens, beginning with a letter. The helper reads subnet/SG IDs, key/table/repository ARNs, actual RDS identity, and trusted ALB subnet CIDRs from the retained data stack. Optional phone identifiers are omitted from API environment when blank. If the public hosted zone is omitted, an operator must publish the two ALB aliases before public readiness checks can pass. Secret ARN existence does not prove its keys, database privileges, or provider access are valid.

## Main deployment, redeployment, and rollback

`AWS deploy` follows a successful **Checks** workflow on main. Eligibility also requires own-repository/main origin and `AWS_STAGING_READY=true`. Before AWS credentials, current checked-out main deployment controls verify the target equals the workflow/current-main SHA and has a successful exact main-push Checks run. Stale automatic runs skip; manual new deployment must select the current main commit. No historical target checkout replaces today's deployment controls.

The staging build publishes the full 40-character commit tag to an immutable ECR repository. Existing tags are reused rather than overwritten; ECS receives the resolved `repository@sha256:digest`, never `latest`. Action dependencies are pinned to reviewed full commits. Infrastructure guards/tests and pinned `cfn-lint` run without AWS access.

The helper creates a stopped first application stack, runs the fixed one-off migration task with a distinct secret/role, then activates services. Subsequent changes run migration before updating services. Migration failures stop advancement; unknown outcomes require inspection. Change sets use compact JSON within CloudFormation's 51,200-byte inline limit, wait for preparation, and inspect `describe-events` for validation errors before execution. Human-readable source JSON can exceed that inline limit; use the helper's compact serialization. Validation errors remain a failed deployment requiring review.

ECS uses a deployment circuit breaker with rollback. The helper verifies all three services and HTTPS `/api/ready` plus voice `/health`. Liveness `/api/health` cannot substitute for database/auth/recovery readiness. If a completed rollout fails readiness, it restores the previous application template/parameters and **checks readiness again**. Schema migrations and database contents are never rolled back automatically. An old image may reject a newer retained schema or recovery state; failed rollback readiness requires operator intervention and does not count as recovered service. First activation failure leaves services stopped and data retained.

`AWS operations` offers `status`, `logs`, `redeploy`, and `cleanup`, only from main and with `AWS_OPERATIONS_READY=true`. Redeploy requires an existing full-SHA ECR artifact and a main-ancestor commit, keeps current deployment controls, and does not run schema migration backward. An optional exact digest must match the artifact; arbitrary tags/digests are rejected. Production deploy/redeploy remains blocked. A future production promotion must supply independently reviewed immutable artifact/digest and preserve the production gate until acceptance is complete.

Cleanup requires the exact `namespace-environment-app` string. It deletes only that application stack and waits for completion. It preserves the database, recovery authority, networking/private zone, encryption key, image repository, audit records, and retained application logs. Retained physical log-group names can prevent recreating the same logical resources after full cleanup: inspect/import them through a reviewed change set or choose a reviewed fresh namespace. Do not remove retained logs merely to make recreation succeed. Data removal, key deletion, snapshot expiry, secret deletion, OIDC/bootstrap removal, and cost shutdown are separate human-controlled procedures.

## Recovery and observability

API/worker roles can read the authority table only under `INSTALLATION#<installation UUID>` and call `rds:DescribeDBInstances` for the bound instance. Application code fixes the manifest sort key. **DynamoDB `LeadingKeys` restricts partition keys, not sort keys**; IAM does not enforce `SK=MANIFEST`. Store only minimal recovery evidence in that partition and review this residual read scope. Runtime and GitHub cannot append journal decisions or approve recovery.

The human policy examples in [infra/aws/policies](../infra/aws/policies) require explicit placeholder replacement and account-specific IAM validation before attachment; they create no role or trust relationship. The privacy operator permits partition-bound reads plus conditional transaction item writes; the separate manifest operator permits partition-bound manifest creation/rotation. Neither grants table deletion or service credentials. IAM likewise cannot distinguish allowed sort keys within that partition: the operator's fixed conditional SDK implementation and reviewed custody provide the append/manifest discipline. Do not grant either policy to runtime/GitHub. See [privacy/recovery operations](PRIVACY_OPERATIONS.md) for explicit operator CLI input, database identities, quarantine, replay, and external security approval.

CloudWatch task logs are encrypted, retained 30 days, and survive application cleanup. WAF request sampling is disabled, and no body/access-log export is enabled. The app must continue emitting bounded redacted operational records; infrastructure does not sanitize arbitrary future log messages. `logs` queries only the last 15 minutes and emits bounded event/code counts, never `@message`, transcripts, names, numbers, headers, XML, tokens, or secret values. Protected console links support deeper authorized inspection. CloudTrail records management changes in the retained versioned audit bucket.

Alarms cover API/voice unhealthy targets and API p99 latency. No notification destination has been configured; assign reviewed alarm actions/escalation ownership before the pilot. Missing metrics do not establish health. Review ECS stopped-task details and migration outcomes in the protected console. Confirm safe diagnostic access, log retention/expiry, and recovery-table integrity monitoring during account setup.

## Required acceptance before enabling a pilot

- Verify CloudFormation change sets, IAM scope/boundaries/service-linked prerequisites, protected environments/main restrictions, and first-deployment failure/rollback paths against the actual account.
- Verify the built image, native role separation, Auth0 MFA/membership revocation, RDS CA/hostname validation, actual resource identity, and mandatory quarantine when recovery authority or its coverage is unavailable.
- Exercise a real restored database under a rotated external epoch, replay every contiguous deletion decision, reconstruct current security independently, and verify old grants/sessions/actions cannot resume. A migration success or manual checkpoint edit is insufficient.
- Test public/internal normal and encoded paths, trusted-proxy spoof rejection, WAF Auth0/Twilio callback compatibility, ALB WebSocket idle/draining behavior, and unavailable providers.
- With explicit phone configuration, verify one dedicated test number before forwarding a restaurant number. Keep reservation integrations, calling/actions/transfers, recording, and biometrics disabled until their specific access and acceptance gates are met.
- Confirm expected cost, budget/alert ownership, retained-resource lifecycle, backups, restoration, and application cleanup/recreation.

Current account-free evidence: all three templates pass `cfn-lint` 1.57.1, custom retention/isolation/workflow guards, and infrastructure unit tests. These checks do not claim a successful AWS deployment or live-provider test.
